# AI English Tutor 课程设计重构建议

审查日期：2026-09-11

> 状态：暂缓，不作为当前产品路线。项目现阶段继续定位为“场景对话练习”，本文仅保留为以后重新评估课程产品时的备选材料。

## 结论

当前的“场景化对话闯关”不适合继续承担整个产品的课程主轴。餐厅、问路、面试等场景仍然有价值，但应该从“课程本体”降为“综合应用与迁移测试”。

课程主轴应该改为：**围绕用户真实口语能力缺口组织的短课，每节课只解决一个可观察、可重练的问题；场景只负责提供语境。**

更准确的产品定位可以是：

> 一个会听你说、找出最值得改的一点、陪你立即重说，并在之后安排复习的 AI 口语教练。

这比“与 Live2D 角色完成场景闯关”更接近用户持续使用的理由。角色、语音和自然对话仍然是体验优势，但课程价值来自诊断、反馈、重练和进步记录。

## 为什么当前场景模式让人感觉不合适

### 1. 场景是话题分类，不是可学习的技能

当前有 16 个场景，每个场景又配置 A1-C2 六个版本、三幕结构、目标词、角色、twist 和完成规则。用户看到的是“餐厅点餐”，但系统没有明确告诉他这节课究竟练：

- 礼貌请求句型；
- 听懂服务员的追问；
- 数量和规格表达；
- 发音；
- 流利度；
- 还是临场应变。

一次对话同时想覆盖多个目标，最后只能用“说过多少目标词”作为评分代理。这个指标容易实现，却不能代表口语能力提高。

### 2. 对话缺少教学闭环

当前主要循环是：AI 说一句 → 用户回应 → AI 继续剧情。系统 prompt 虽然要求温和纠错，但响应结构没有专门的错误、反馈、重说和掌握证据字段，UI 也没有“立即再说一次”的教学动作。

一节有效的口语短课至少需要：

1. 给一个清晰任务；
2. 用户第一次尝试；
3. 只指出最值得修正的一点；
4. 给出可理解的示范；
5. 用户立即重说；
6. 换一个语境再次使用；
7. 记录是否独立完成。

当前系统通常在第 2 步后直接继续剧情，学习机会被自然对话吞掉了。

### 3. “保持角色”与“当老师”存在冲突

场景 prompt 强调 stay in character、不要解释目标、自然推进三幕，同时还要求塞目标词、翻译、例句、提示和动作。服务员如果停下来讲语法会破坏沉浸感；如果始终扮演服务员，又无法做好纠错。

更合理的方式是明确两种状态：

- **练习状态**：AI 扮演对话角色，保持自然互动；
- **教练暂停**：角色暂时退出剧情，用很短的反馈指出一个问题，并让用户重说。

用户应当看得懂何时在练、何时在学。

### 4. A1-C2 只是语言复杂度标签，没有形成能力递进

当前同一场景通过换 setting、twist、词汇和角色扩展到六个 CEFR 档，但 CEFR 的区别不只是词更难。真正的递进还包括：

- 任务需要完成多少信息交换；
- 能否主动追问和澄清；
- 能否解释原因、比较选项、处理误解；
- 准确度、流利度和互动策略要求；
- 支架从完整句、句框、关键词逐步撤除。

只把“餐厅”从简单点单升级为投诉协商，仍然没有证明用户掌握了中间能力。

### 5. 课程完成与学习成果脱节

当前完成规则围绕 targetWords、覆盖率、轮数和星级。代码还把老师使用的目标词计入 wordsUsed，因此指标本身存在实现错误；即便修复，它最多证明学生在一个剧本里说过某些词，不能证明学生能在新情境中独立使用。

课程结果应该回答：

- 用户今天能做什么以前做不到的事；
- 哪一个问题已经通过重练；
- 哪一个问题仍需复习；
- 下一节为什么推荐给他。

### 6. 内容规模增长过快，教学质量难以维护

16 场景 × 6 等级已经形成 96 个场景变体，每个变体又含多幕、主题和 twist。继续扩充会让大部分精力花在配置剧情，而不是打磨纠错质量、评估稳定性和学习路径。

场景内容可以由模型变化生成；真正应该由产品明确维护的是有限的技能图谱、评分量规和练习模板。

## 推荐的新课程模型

### 三层结构

| 层级              | 作用                     | 示例                                                 |
| ----------------- | ------------------------ | ---------------------------------------------------- |
| 学习目标 Skill    | 定义本节真正要提升的能力 | 礼貌提出请求；用过去时讲经历；追问细节；/θ/ 发音     |
| 练习活动 Activity | 决定教学动作和反馈方式   | 跟读、替换练习、引导回答、信息差对话、自由表达、重说 |
| 语境 Context      | 让技能有真实用途         | 餐厅、会议、旅行、兴趣、用户自己的工作               |

同一个 Skill 可以在多个 Context 中练习。例如“礼貌请求”先在咖啡店练，再迁移到酒店和同事协作；这比把三个地方做成三门彼此独立的课程更容易形成掌握证据。

### 技能图谱先保持小而清楚

MVP 不需要完整语言学体系。建议从 20–30 个高频口语技能开始，分为五类：

| 能力类       | 初始技能示例                                                        |
| ------------ | ------------------------------------------------------------------- |
| 互动策略     | 开启对话、追问、澄清、确认理解、轮流表达、结束对话                  |
| 语言功能     | 请求、拒绝、建议、比较、描述经历、解释原因、表达观点                |
| 核心语法     | be/do 问句、一般过去时、将来计划、可数与数量、情态动词、条件句      |
| 词块与搭配   | I'd like…, Could you…?, It depends on…, What I mean is…             |
| 发音与流利度 | 句子重音、词尾音、连读、停顿、常见难音；能力受 ASR/音频评估条件限制 |

每个 Skill 至少定义：前置技能、适用 CEFR、示例输入、成功标准、常见错误、反馈策略和迁移任务。CEFR 用于推荐难度，不作为课程目录本身。

## 一节 8–12 分钟短课应该怎样进行

### 1. Check-in：确定今天的目标

用户可以选择“工作沟通”“旅行”“随便聊聊”，系统也可以根据上次错误推荐一个目标。首页要先回答“今天练什么”，而不是先展示 16 个场景。

### 2. Diagnostic attempt：先说一次

给用户一个真实而明确的任务，例如：

> 你想把饮料换成无糖的，请向店员说明。

不先讲答案。用户第一次尝试用于判断是否需要教学。

### 3. Focused feedback：只纠正一件事

一次优先处理一个高价值问题，推荐优先级：

1. 意思是否表达成功；
2. 是否容易产生误解；
3. 本节目标技能是否正确；
4. 高频且可立即修复的问题；
5. 低影响的小语法错误。

反馈格式保持短：肯定已完成的部分 → 指出一个差距 → 给一个自然版本。不要每轮罗列全部错误。

### 4. Repair：立即重说

让用户重新说同一个意思。可以按需要提供三级支架：

- 一级：只提醒意图；
- 二级：提供关键词或句框；
- 三级：完整示范，可跟读。

只有用户重说后，系统才有资格记录“已修正”。直接点击完整提示继续剧情不算独立掌握。

### 5. Variation：换一个条件再说

改变对象、数量、时间或态度，验证用户不是只复述答案。例如从“换无糖饮料”变成“询问有没有不含奶的选择”。

### 6. Mini role-play：用场景进行综合应用

此时才进入 3–5 轮场景对话。场景不再背负整节课，只用于让用户在自然交互中应用刚练过的技能。

### 7. Recap：给可行动的结果

结束页只显示少量可信信息：

- 今天练了什么；
- 第一次表达与改进版本；
- 是否在新情境中独立完成；
- 一个待复习项；
- 下一次建议。

不建议继续用 3/4/5 星评价目标词覆盖率。可以改成：**需要帮助 / 提示后完成 / 独立完成 / 能迁移使用**。

## 产品应提供的三种入口

### 今日练习（默认入口）

系统依据最近错误、到期复习和用户目标，生成一节短课。这是长期留存的主入口。

### 自由对话

用户自由聊感兴趣的话题。系统后台观察表现，每 2–3 轮最多给一次关键反馈；结束后抽取候选学习目标。自由聊天用于表达和诊断，不应偷偷按未说出的词扣分。

### 情境挑战

保留现有餐厅、面试、投诉等内容，但改成阶段性应用测验。挑战前显示要用的能力，不预先展示必须塞入的 30 个词；挑战后按任务完成、互动策略、目标技能和可理解度反馈。

## 反馈策略需要让用户选择

不同学习者对打断的接受度差异很大，建议提供三档：

| 模式     | 行为                             | 适合                   |
| -------- | -------------------------------- | ---------------------- |
| 流畅优先 | 对话中不打断，结束后总结 1–2 点  | 克服开口焦虑、自由聊天 |
| 平衡模式 | 影响理解或命中本节目标时暂停纠正 | 默认模式               |
| 精准模式 | 更频繁纠正并要求重说             | 面试准备、刻意练习     |

这比把“温和纠正”写在 prompt 里更可控，也更符合真实教学偏好。

## 新的掌握与推荐逻辑

### 掌握证据

一个 Skill 的单次练习结果可记录为：

- `attempted`：尝试过；
- `completed_with_model`：跟完整示范完成；
- `completed_with_hint`：借助关键词或句框完成；
- `independent`：无提示完成；
- `transferred`：在变化语境中独立完成。

只有 independent/ transferred 才应显著增加掌握度。老师在回复中使用某个词、用户点击完整建议、用户没有遇到某个复习项，都不构成掌握或失败证据。

### 下一课推荐

推荐优先级可以先使用透明规则，无需复杂模型：

1. 到期且此前能独立完成的技能复习；
2. 上节未完成的单一技能；
3. 用户目标路径中的下一个技能；
4. 自由对话中新发现的高频问题；
5. 用户主动选择的兴趣话题。

## 建议的响应契约

不要让一个 `TeachingResponse` 同时承载聊天、课程判断、词汇、动画和所有教学语义。至少把教学事件结构化：

```ts
type TutorAction =
  | { type: 'conversation'; text: string; translation?: string }
  | {
      type: 'feedback'
      praise?: string
      issue: { category: string; original: string; improved: string; explanationZh: string }
      repairPrompt: string
      supportLevel: 0 | 1 | 2 | 3
    }
  | { type: 'lesson_step'; step: 'attempt' | 'repair' | 'variation' | 'roleplay' | 'recap' }

interface AttemptAssessment {
  skillId: string
  outcome: 'not_demonstrated' | 'with_model' | 'with_hint' | 'independent' | 'transferred'
  evidence: string
  confidence: number
}
```

动画信息可以作为展示 metadata，不能影响教学状态机。LLM 给出 assessment 建议后，服务端还应基于当前 step、提示使用情况和用户原话做约束，避免完全相信模型自评。

## 数据模型建议

建议逐步引入：

- `skills`：稳定的技能定义；
- `lesson_templates`：短课步骤和练习活动；
- `lesson_sessions`：本节目标、当前步骤、反馈模式；
- `attempts`：用户原话、提示级别、评估、重说关系；
- `skill_mastery`：按技能聚合的掌握度和下次复习时间；
- `learner_profile`：目标、兴趣、反馈偏好、可选的长期弱项；
- `contexts`：复用现有场景数据，但只保存角色和情境素材。

对话历史与学习证据要分开。历史用于给 LLM 上下文，attempts 用于可解释的进步判断；不能继续从聊天消息反推所有学习状态。

## 对现有资产的处理

不需要推倒重来：

| 现有资产                       | 处理方式                                                 |
| ------------------------------ | -------------------------------------------------------- |
| Live2D、TTS、ASR、SSE、聊天 UI | 保留，作为交互层                                         |
| 16 个场景及角色设定            | 精简为 Context，供 mini role-play 和挑战使用             |
| levelProfiles                  | 提取任务复杂度和语言支架；停止为每个场景维护六套完整剧情 |
| targetWords、wordsUsed、星级   | 停止作为主要学习指标；可迁移为某些词块技能的素材         |
| studentReplyHints              | 改为分级支架，并记录用户用了哪一级提示                   |
| 场景暂停/续玩                  | 对 8–12 分钟短课价值较低，可先冻结开发                   |
| 词汇数据库和复习调度           | 保留数据，修正语义；逐步迁移到 Skill mastery             |
| 自由对话引擎                   | 保留，增加会话末诊断和下一课建议                         |
| 场景引擎                       | 改造成 RolePlayActivity/Challenge，而不是课程总引擎      |

## 分阶段落地

### 第 0 阶段：先验证教学方向，不大改架构（约 3–5 天）

选一个高频技能，例如“礼貌提出请求”，手写一条 6 步短课。复用现有聊天和语音，只新增 lesson step、反馈卡和重说按钮。找 3–5 次真实使用记录，观察用户是否愿意重说、是否能在 variation 中独立完成。

成功信号：用户完成至少一次 repair；第二个变体比第一次更少依赖提示；用户能说出自己本节学到了什么。

### 第 1 阶段：建立最小课程内核（约 1–2 周）

- 定义 10 个 Skill 和 3 种 Activity；
- 新增 lesson session 与 attempt 记录；
- 实现 attempt → feedback → repair → variation → recap 状态机；
- 提供平衡反馈模式；
- 首页默认进入“今日练习”；
- 用 3 个现有场景作为 role-play 语境。

### 第 2 阶段：个性化推荐（约 1–2 周）

- 到期复习与 skill mastery；
- 自由对话结束后的候选问题提取；
- 用户目标路径；
- 支架自动升降；
- 可解释的下一课推荐。

### 第 3 阶段：重做挑战与发音（方向验证后）

- 将场景改成综合挑战量规；
- 根据用户真实音频能力决定是否加入发音评分；
- 比较首次尝试、重说和迁移表现；
- 再决定是否需要长期记忆、proactive 或更多角色。

## 当前建议暂停的工作

在课程闭环验证前，建议暂停：

- 继续增加场景和六档剧情配置；
- 优化三幕推进、目标词分桶、场景星级；
- 基于场景进度做 proactive；
- 扩大长期记忆范围；
- 把更多时间投入角色 Provider 或新 LLM Provider。

这些功能可能提升丰富度，但不会解决“用户究竟学到了什么”。优先级应是：**一次尝试能被准确反馈，一次反馈能触发重练，一次重练能留下可信证据。**

## MVP 验收指标

先采用能反映学习行为的指标：

- 短课完成率；
- 首次尝试后进行 repair 的比例；
- repair 成功率；
- variation 中无提示完成率；
- 7 天后同一 Skill 的复习成功率；
- 用户每周独立完成的技能数；
- 用户对反馈“有帮助 / 不准确”的评价。

平均会话时长和场景完成率可以继续观察，但不应作为课程质量的核心指标。更长的聊天可能只是 AI 说得更多，并不代表用户学得更多。
