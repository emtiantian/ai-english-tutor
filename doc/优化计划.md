# AI English Tutor 优化计划

参考开源项目:
- [moeru-ai/airi](https://github.com/moeru-ai/airi)(Live2D + VRM 双角色、20+ LLM provider、浏览器内推理、MCP Launcher)
- [Open-LLM-VTuber/Open-LLM-VTuber](https://github.com/Open-LLM-VTuber/Open-LLM-VTuber)(Live2D 桌宠、VAD + 语音打断、视觉感知、内心独白、proactive)

---

## 总览

本计划涵盖 **7 项功能借鉴**,按交付波次组织。每项都给出:目标 → 现状 → 实现方案 → 任务拆解 → 风险 → 验收标准。

### 迭代波次与优先级

| 波次 | 项目 | 借鉴自 | 工作量 | 优先级 |
|---|---|---|---|---|
| **P1 沉浸感** | ① 内心独白 → 动作触发 | Open-LLM-VTuber | S(2-3d) | 🔴 High |
| **P1 沉浸感** | ② VAD + 语音打断 | Open-LLM-VTuber | M(4-5d) | 🔴 High |
| **P2 教学增强** | ⑥ Proactive 主动开口 | Open-LLM-VTuber | S(2d) | 🟡 Med |
| **P2 教学增强** | ⑦ 长期记忆 / 学习画像 | airi(Memory Alaya) | L(7-10d) | 🟡 Med |
| **P3 性能/扩展** | ④ ASR 流式 + 本地选项 | Open-LLM-VTuber | M(4-5d) | 🟡 Med |
| **P3 性能/扩展** | ⑧ 多老师角色卡 | airi(隐含) | S(2-3d) | 🟢 Low |
| **P4 重构** | ⑪ LLM provider 统一(xsai 风格) | airi | M(3-4d) | 🟢 Low |

> S = 1-3d / M = 3-7d / L = 7+d(单人工作量估计)

### 跨功能依赖关系

```
①内心独白 ─┬─→ ⑥proactive (复用 motion tag 系统让主动消息也带情感)
           └─→ ⑧多老师 (不同人设触发不同表情风格)

②VAD打断 ──→ ④ASR流式 (流式 ASR 是更顺滑的打断体验)

⑦长期记忆 ──→ ⑥proactive (主动开口靠记忆驱动选话题)
           └─→ ⑧多老师 (per-character 记忆隔离)

⑪provider统一 ──→ 独立,不阻塞其他功能,可放最后
```

### 全局风险

- **音频管线复杂度**:VAD + 打断 + 流式 ASR 三者交织在同一条录音/播放链路上,需要分阶段引入,**不要混在一个 PR 里**
- **prompt 系统膨胀**:多个功能(内心独白、proactive、角色卡)都需要改 `ai/prompts/teaching.ts`,先统一 prompt 注入机制再加功能
- **会话状态膨胀**:`SessionManager` 已经承担会话 + 场景 + 词汇,再加长期记忆 + 角色卡可能撑爆,⑦ 上线前考虑拆分

## ① 内心独白 → 动作/表情触发 【P1】

### 目标 / 用户体感

老师回复里出现 `*微笑*`、`*nodding*`、`(竖起大拇指)` 这类 inline action tag 时,Live2D 角色立即触发对应的表情/动作,而不是只显示文字。

**对比**:Open-LLM-VTuber 把 inline thought 单独渲染并驱动表情;我们当前是用 `motion-analyzer` 从纯文本启发式推测(不准、易冲突)。

### 现状评估

- 已有:`packages/shared/src/motion-analyzer.ts` 文本→motion 启发式映射
- 已有:`packages/shared/src/types.ts` 中 `AVAILABLE_MOTIONS` / `AVAILABLE_EXPRESSIONS` 定义语义动作/表情集合；具体模型映射由各 Live2D manifest 的 `motionRegistry` 提供
- 已有:SSE event `teacher.response` 含 `motion` / `expression` 字段
- 缺:**LLM prompt 没有要求输出显式 action tag**,完全靠后端二次猜测;不同模型行文风格差异巨大,启发式失败率高

### 实现方案

**关键思路**:把"猜"改成"约定"。在 system prompt 里要求 LLM 用约定语法输出动作,后端解析这些 tag 而不是文本本身。

**协议设计**(inline tag,流式友好):

```
Great pronunciation! *smile* Let's try the next sentence.
                    ^^^^^^^^
                    解析为 motion=happy, expression=smile
```

支持的 tag 集合定义在 `packages/shared/src/types.ts` 的 `AVAILABLE_MOTIONS` / `AVAILABLE_EXPRESSIONS` 中，LLM 只能从中选(prompt 白名单 + 后端兜底过滤)。

**Stream 解析**:tag 可能跨 chunk 切开,流式时用状态机缓冲半截 tag,完整后再 emit `teacher.motion` 事件。

### 任务拆解

- [ ] **T1.1** 在 `packages/shared/src/types.ts` 的 `AVAILABLE_MOTIONS` / `AVAILABLE_EXPRESSIONS` 基础上给每个 motion/expression 加 `triggerTag` 字段(如 `"smile"`, `"nod"`),并暴露白名单 list
- [ ] **T1.2** `apps/tutor-server/src/ai/prompts/teaching.ts` 加 system 段落:列出可用 tag,要求 LLM 自然嵌入文本
- [ ] **T1.3** 新增 `apps/tutor-server/src/ai/inline-tag-parser.ts`:输入 chunk 流,输出 `{ visibleText, motions[] }`(状态机,处理 tag 跨 chunk)
- [ ] **T1.4** 在 `engine.ts` 流式回复路径调用 parser,过滤掉 tag 文本只推 `visibleText`,同时为每个 motion 单独推 `teacher.motion` SSE event
- [ ] **T1.5** 前端 `App.vue` / Live2D Provider 监听 `teacher.motion` 立即触发动作(不再等回复结束)
- [ ] **T1.6** **降级**:LLM 一句话里没出现任何 tag 时,**保留** `motion-analyzer` 作为兜底
- [ ] **T1.7** 单测覆盖 parser 的 6 个边界(无 tag、单 tag、跨 chunk、未闭合、连续多 tag、混入 markdown)

### 风险与依赖

- LLM 不一定听话 → 多模型适配(deepseek/xiaomi/openai 输出风格不同),需要在 prompt 里用 few-shot 强约束
- tag 协议要简单 → **用 `*xxx*` 不用 XML**,避免误触发 markdown 斜体(建议 `[motion:smile]` 这种不歧义形式,最终定稿在 T1.1 讨论)

### 验收标准

- 5 种典型场景(打招呼/纠错/鼓励/思考/告别)每个跑 10 次,**≥80%** 触发正确 motion
- 流式打字过程中 motion 在 tag 完成时立即触发,**不等整句结束**
- tag 文本不显示在 chat UI 里

## ② VAD + 语音打断 【P1】

### 目标 / 用户体感

- 用户不需要按住按钮,**说一句停一下,老师自动开始回复**
- 老师正在说话时,用户开口立即把老师的 TTS 静音并打断当前 LLM 请求,**像真人对话**

**对比**:Open-LLM-VTuber 的 `voice interruption without headphones` 是其招牌功能;我们目前应该是 push-to-talk(需确认)。

### 现状评估

- 已有:`apps/tutor-app/src/composables/useAudioRecorder.ts`(录音)、`useAudioPlayback.ts`(播放)
- 已有:`audio/recorder.ts` 和 `audio/player.ts`
- 缺:**没有 VAD**,需要用户主动按按钮录音
- 缺:**没有打断机制**,老师 TTS 在播,LLM stream 在推,用户开口被完全忽略

### 实现方案

**前端 VAD**:用 [`@ricky0123/vad-web`](https://github.com/ricky0123/vad)(Silero VAD 的 WASM 封装,~1MB,浏览器端跑)

- 持续监听麦克风(可由用户开关)
- `onSpeechStart`:暂停 TTS 播放、abort 当前 SSE/LLM 请求、开始累积 audio chunks
- `onSpeechEnd`:把累积的 audio 上传 ASR(短停顿 800-1500ms 触发)

**打断管线**(三层抓手):
1. **TTS 播放**:`useAudioPlayback.ts` 暴露 `abort()`,清空 AudioContext queue
2. **LLM SSE**:`tutor-client` 持有当前 `AbortController`,VAD `onSpeechStart` 触发 abort
3. **后端**:接收到 abort signal 后,`engine.ts` 把当前会话标记为 `interrupted`,session 历史里保留**已生成的部分回复**(给 LLM 自然续接)

**echo cancellation**(避免老师声音被 VAD 误判):
- `getUserMedia({ audio: { echoCancellation: true, noiseSuppression: true } })` 浏览器原生 AEC 大部分场景够用
- 边缘场景:在播放 TTS 期间临时降低 VAD 灵敏度,或基于音量阈值二次过滤

### 任务拆解

- [ ] **T2.1** 引入 `@ricky0123/vad-web`,封装 `composables/useVAD.ts`,暴露 `onSpeechStart/End` 事件 + `enable/disable`
- [ ] **T2.2** 设置项:`pages/Settings.vue` 加"免提对话(beta)"开关,默认关
- [ ] **T2.3** `useAudioPlayback.ts` 加 `abort()` 方法,清空 AudioContext queue + 标记中断
- [ ] **T2.4** `tutor-client.ts` 维护 currentAbortController,暴露 `interrupt()` 方法
- [ ] **T2.5** `stores/tutor.ts` 监听 VAD 事件,组合调用 `playback.abort() + client.interrupt() + recorder.start()`
- [ ] **T2.6** 后端 `routes/chat.ts` + `engine.ts`:接收新 endpoint `POST /api/chat/interrupt`,把当前 session 标记为打断状态,保留已生成内容到会话历史
- [ ] **T2.7** SSE `teacher.interrupted` 事件用于前端 UI 反馈("被打断了…")
- [ ] **T2.8** 集成测试:模拟"老师说一半,用户开口"场景,断言 TTS 停止、LLM abort、新 ASR 请求开始
- [ ] **T2.9** iOS Safari 适配:VAD 需要在 user gesture 后启动 AudioContext(已有 unlock 机制,复用)

### 风险与依赖

- **AEC 不够好导致老师自己打断自己**:这是 Open-LLM-VTuber 也承认的难题,先用浏览器原生 AEC + 播放时降灵敏度,实在不行加"按住空格强制录音"逃生入口
- **VAD WASM 模型 1MB+**:首次加载延迟,放 lazy import,只在开关打开时下载
- **会话状态机变复杂**:多了 `speaking → interrupted → resuming` 几个状态,要在 `session-manager` 里画清楚

### 验收标准

- 安静环境下用户说话延迟 < 300ms 触发录音
- 老师 TTS 播放中,用户开口 < 500ms 内 TTS 静音
- 被打断后,LLM 不再生成,token 不会浪费
- 误触发率 < 5%(在键盘敲字 / 鼠标点击噪音下)

## ④ ASR 流式 + 本地选项 【P3】

### 目标 / 用户体感

- **流式 ASR**:用户说话过程中实时出现字幕,而不是整段说完后再等 1-2s
- **本地 ASR 选项**:用 sherpa-onnx / Faster-Whisper 实现完全离线、低延迟

### 现状评估

- 已有:`voice/providers/whisper-asr.ts` 整段 POST(批处理)
- 已有:`voice/providers/xiaomi-asr.ts` / `browser-asr.ts`
- 缺:**没有流式 ASR provider**(Whisper.cpp 支持 streaming,只是我们没开)
- 缺:**没有本地 ONNX runtime 路径**

### 实现方案

**流式协议**:WebSocket(后端 ↔ 前端),协议:
- C → S: `{ "type": "audio", "chunk": <pcm/base64> }` 每 200ms 一次
- S → C: `{ "type": "partial", "text": "..." }` 实时字幕
- S → C: `{ "type": "final", "text": "...", "confidence": 0.95 }` 一句话结束

**provider 选型**:
- **sherpa-onnx**:ONNX runtime,跑 Zipformer / Paraformer 模型,中英文模型都有,**支持流式**,CPU 上 ~real-time
- **Faster-Whisper**:CTranslate2 加速 Whisper,延迟比 OpenAI Whisper 低 4-5x,但**不是真流式**(chunked streaming)

**集成路径**:由于我们 Node 后端,sherpa-onnx 有官方 [Node binding](https://github.com/k2-fsa/sherpa-onnx#nodejs-typescript-api),无需另起 Python 服务。

### 任务拆解

- [ ] **T4.1** `voice/asr.ts` 工厂扩展:加 `streaming?: ASRStreamingProvider` 接口
- [ ] **T4.2** `voice/providers/sherpa-asr.ts`:用 `sherpa-onnx-node` 实现流式 provider,模型放 `DATA_DIR/models/sherpa-onnx/`
- [ ] **T4.3** 新路由 `routes/voice-stream.ts`:基于 `@fastify/websocket`,持有每会话 sherpa 实例
- [ ] **T4.4** 前端 `composables/useStreamingASR.ts`:每 200ms 切 PCM chunk 推 WebSocket,onMessage 写到 `stores/tutor.partialTranscript`
- [ ] **T4.5** UI:`ChatPanel.vue` 显示 partial text(淡色) → final text(实色)
- [ ] **T4.6** 部署:`docker-compose.yml` 加 `sherpa-onnx` 模型挂载,部署脚本自动下载模型
- [ ] **T4.7** `.env.example` 加 `ASR_PROVIDER=sherpa-onnx` + 模型路径配置
- [ ] **T4.8** Whisper provider 保留为后备,允许配置切换

### 风险与依赖

- sherpa-onnx Node binding 在 macOS arm64 上的 prebuilt 偶尔有坑,**先在 docker linux 跑通**再适配本地 dev
- 模型大小 ~150-300MB,docker image 不要打包,通过 volume 挂载(参考现有 whisper 模型下载流程)
- 部分场景(吵闹环境)流式准确率低于批量 → 提供 `streaming: 'auto'` 让用户在质量/延迟间切换

### 验收标准

- 流式 partial 延迟 < 300ms,final 延迟 < 800ms
- CPU only 跑 zipformer-small 模型,real-time factor < 0.5(说 1 秒处理 < 0.5 秒)
- 离线场景(无外网)完全可用

## ⑥ Proactive 主动开口 【P2】

### 目标 / 用户体感

- 用户静默 N 秒,老师主动说话:"You seem quiet, want to try another sentence?"
- 用户连续犯同类错误,老师主动指出:"I noticed you struggle with 'th' sound, let's practice it"

**对比**:Open-LLM-VTuber 的 proactive 是无条件触发;我们做**教学场景驱动**会更有价值。

### 现状评估

- 已有:`SessionManager` 维护会话历史
- 已有:`VocabTracker` 跟踪场景词汇进度
- 缺:**前端没有 idle timer**
- 缺:**没有 proactive prompt 模板**

### 实现方案

**触发条件**(由前端检测,后端生成内容):
1. **静默触发**:用户 30s 无任何输入(语音/打字)→ 调用 `/api/chat/proactive`
2. **进度触发**:场景词汇进度卡住超过 3 轮 → 老师主动给提示
3. **错误模式触发**:`VocabTracker` 记录到同一发音错误 ≥ 2 次 → 主动开口

**实现**:
- 后端新增 `engine.proactive(sessionId, reason)` 方法,根据 reason 选不同 prompt 模板
- 前端 `stores/tutor.ts` 加 idle timer,phase 为 `teaching` 时启动
- LLM 输出走和普通回复完全一样的 SSE 通道,前端无需特殊处理(只是看起来"AI 自己说话了")

### 任务拆解

- [ ] **T6.1** `ai/prompts/proactive.ts` 新模板,接受 `reason: 'idle' | 'stuck' | 'error-pattern'` 切换风格
- [ ] **T6.2** `engine.ts` 加 `proactive(sessionId, reason, context?)` 方法
- [ ] **T6.3** 新路由 `POST /api/chat/proactive` body `{ sessionId, reason }`,触发后通过 SSE 推回复
- [ ] **T6.4** 前端 `useIdleTimer.ts` composable:监听用户输入,N 秒无活动触发回调
- [ ] **T6.5** `stores/tutor.ts` 注册 idle timer,phase=teaching 时启动,N 默认 30s 可配置
- [ ] **T6.6** `VocabTracker` 加 `getStuckPattern()` API 检测错误重复
- [ ] **T6.7** UI 提示:proactive 消息用稍微不同的样式(如左侧加 "💭" 图标)区分

### 风险与依赖

- 太烦人:proactive 频率必须有节流(同一会话 5 分钟内最多 2 次)
- 用户在思考(不是真的 idle):区分"思考中"和"走神",N 默认 30s 而非 10s
- **依赖 ① 内心独白**:proactive 消息也走 motion tag,触发"招手 / 戳一戳"动作更生动

### 验收标准

- idle 30s 触发率 100%,但同会话节流生效
- 用户开始输入后 idle timer 立即重置
- 教学连续性:proactive 内容能引用前面的对话(不是 hello 寒暄)

## ⑦ 长期记忆 / 学习画像 【P2】

### 目标 / 用户体感

- 老师记得"上次说你 'th' 发音不准"、"你说过你喜欢旅行场景"、"你的目标是雅思 6.5"
- 跨会话学习画像:词汇掌握度、薄弱发音、偏好场景、对话风格(formal/casual)

**对比**:airi 的 `Memory Alaya` 是 WIP,用 DuckDB WASM + pgvector;我们后端有 SQLite,加 `sqlite-vec` 比纯浏览器方案更可控。

### 现状评估

- 已有:`SessionManager` SQLite 持久化(但只存对话,不存抽象 fact)
- 已有:`VocabTracker` 词汇掌握度(隐式记忆)
- 缺:**没有 fact 抽取**
- 缺:**没有向量检索**

### 实现方案

**数据模型**(SQLite):

```sql
-- 用户画像(每用户一行)
CREATE TABLE user_profile (
  user_id TEXT PRIMARY KEY,
  cefr_level TEXT,            -- 当前评估等级
  goals TEXT,                 -- 'IELTS 6.5', 'travel chat'
  preferences JSON,           -- 学习偏好
  updated_at INTEGER
);

-- 记忆条目(向量检索)
CREATE TABLE memories (
  id INTEGER PRIMARY KEY,
  user_id TEXT NOT NULL,
  kind TEXT,                  -- 'fact' | 'weakness' | 'preference' | 'achievement'
  content TEXT,               -- 自然语言事实
  embedding BLOB,             -- sqlite-vec
  source_session TEXT,
  importance INTEGER,         -- 0-10,低重要性会被淘汰
  created_at INTEGER,
  last_accessed INTEGER
);

CREATE VIRTUAL TABLE memories_vec USING vec0(embedding float[768]);
```

**写入路径**(每次会话结束):
1. `engine.ts` 调 `memory-extractor.ts`,用 LLM 把这次会话总结成 3-5 条 fact(prompt 模板约束输出 JSON)
2. 对每条 fact 算 embedding(用 OpenAI text-embedding-3-small 或本地 ONNX)
3. 写入 `memories` 表

**读取路径**(每次会话开始 / 长回合):
1. 取当前用户最近输入向量化
2. `sqlite-vec` top-K 召回 5 条最相关记忆
3. 注入 system prompt:`Background about this student: ...`

**淘汰策略**:总量上限 200 条/用户,超出按 `importance` + `last_accessed` 时间衰减淘汰。

### 任务拆解

- [ ] **T7.1** 引入 `sqlite-vec` 扩展(better-sqlite3 加载 .so/.dylib),`db/migrations/` 加表 schema
- [ ] **T7.2** `ai/memory/embedder.ts` 抽象 embedding provider(默认 openai,可切本地)
- [ ] **T7.3** `ai/memory/extractor.ts`:会话结束时调 LLM 提取 fact,prompt 严格 JSON 输出
- [ ] **T7.4** `ai/memory/store.ts`:增删改查 + 向量召回 + 淘汰
- [ ] **T7.5** `engine.ts` 集成:会话开始时调 `store.recall()` 注入 prompt,会话结束触发 `extractor.extract()`(异步,不阻塞响应)
- [ ] **T7.6** UI 新增"学习画像"页面:展示已记录的 fact,允许用户编辑/删除(隐私 + 准确性)
- [ ] **T7.7** 数据导出/导入:用户可下载 JSON 备份
- [ ] **T7.8** 默认 user_id 用浏览器持久化 ID(没登录系统时),登录后绑定

### 风险与依赖

- LLM 抽取 fact 出错 → 给用户编辑入口(T7.6)兜底
- 隐私:记忆里可能存敏感信息,**默认本地存储,不上传**,部署模式才入 SQLite
- embedding 成本:每会话调一次 embedding API,可换本地 ONNX(`Xenova/all-MiniLM-L6-v2` 23MB)
- **依赖 ⑥ proactive**:proactive 触发时去查记忆,选最相关话题主动开口

### 验收标准

- 连续 3 个会话后,第 4 个会话开始时老师能引用至少 1 条历史 fact
- 记忆召回准确率(人工评估)≥ 70%
- 单用户 1000 条记忆下,召回延迟 < 50ms
- 用户能在 UI 看到、编辑、删除自己的记忆

## ⑧ 多老师角色卡 【P3】

### 目标 / 用户体感

用户在 onboarding 或设置里挑选老师:**Lily(美式年轻女声,友好)/ James(英式中年男声,严师)/ Yuki(日英双语,温柔)…**

每位老师有独立的:人设、TTS 音色、Live2D 模型、教学风格(在 prompt 里)、表情动作触发偏好。

**对比**:airi 的 `character-persona.ts` 已经是模板,但只 1 个默认;我们扩展成多个 + 用户可选。

### 现状评估

- 已有:`packages/shared/src/character-persona.ts` + `persona-default.json`
- 已有:`packages/shared/src/types.ts` + `motion-registry.ts` + 各模型 manifest 中的 `motionRegistry`
- 已有:`docs` 中 `~/.ai-english-tutor/data/persona.json` 覆盖机制
- 已有(2026-06-25 新):`packages/shared/src/models/` 多 Live2D 模型 manifest 系统(A 阶段完成)
- 缺:**只有 1 个默认 persona**,无法运行时切换
- 缺:**TTS 音色和 persona 没绑定**,需手动配 env

### 实现方案

**数据结构**(packages/shared):

```ts
interface TeacherProfile {
  id: string                        // 'lily' / 'james'
  displayName: string
  avatar: string                    // 头像 URL
  persona: CharacterPersona         // 现有结构
  voice: {
    provider: 'xiaomi' | 'cosyvoice' | 'openai'
    voiceId: string                 // provider-specific
    description?: string            // 小米 voicedesign 结构化描述
  }
  characterModel: {
    type: 'live2d' | 'spine' | 'vrm' | 'svg'
    modelId: string                 // 复用 Live2DModelManifest.id(A 阶段完成的清单)
  }
  motionRegistry: MotionRegistry    // 每个老师不同的动作映射(可与模型同源)
  teachingStyle: {
    formality: 'casual' | 'formal'
    correctionStrictness: 'gentle' | 'normal' | 'strict'
    languages: string[]             // ['en'] / ['en', 'zh']
  }
}
```

**存储**:
- 内置 3-5 个 `teachers-default.json`(Lily/James/Yuki/Alex…)
- 用户可在 `~/.ai-english-tutor/data/teachers/` 自定义
- 用户选择持久化到 IndexedDB(`tutor.selectedTeacherId`)

**切换**:
- 切换老师 = 切换 prompt 注入 + 切换 TTS provider 参数 + reload Live2D 模型(用 modelId 走 factory) + reset motion-registry
- **会话级别**:可以在新会话切,**进行中的会话不允许切**(避免上下文撕裂)

### 任务拆解

- [ ] **T8.1** 设计 `TeacherProfile` 类型 + 移动 `character-persona.ts` 到 `teachers/<id>.ts`

### 风险与依赖

## ⑪ LLM Provider 统一(xsai 风格) 【P4 重构】

### 目标

把当前 `providers/deepseek.ts` + `providers/xiaomi.ts` + 未来的 openai/claude/gemini 整合到**统一的薄接口**,减少重复代码 + 容易加新 provider。

**对比**:airi 的 [xsai](https://github.com/moeru-ai/xsai) 是类似 Vercel AI SDK 的极简 LLM client,统一 streaming/tool/multimodal 接口,~5KB。

### 现状评估

- 已有:`apps/tutor-server/src/ai/llm.ts` 定义 `LLMProvider` 接口
- 已有:`providers/deepseek.ts`(13 symbols)、`providers/xiaomi.ts`(14 symbols)
- 痛点:两个 provider 的 stream/audio multimodal/错误重试逻辑**各写各的**,加 openai 时大概率第三遍重复

### 实现方案

**两条路**,推荐 B:

**A. 直接接入 `xsai`**:依赖一个新库,但能力齐(20+ provider 现成)
- 优:零维护
- 缺:外部依赖,我们的 multimodal audio content 格式可能跟 xsai 不完全对齐

**B. 抽内部 unified-client**(推荐):
- 内部抽一层 `UnifiedLLMClient`,所有 provider 用同一个 OpenAI-compatible 调用代码
- DeepSeek/Xiaomi/OpenAI/Moonshot/SiliconFlow/Together 90% 都是 OpenAI 兼容,**一份代码搞定**
- 只对真正不一样的(如 Claude messages API、Gemini Generate API)单独写 adapter
- 优:零外部依赖,完全可控
- 缺:Claude/Gemini 仍需 adapter,但只此两家

**核心抽象**:

```ts
// 新文件:ai/llm/unified-client.ts
interface UnifiedConfig {
  baseURL: string
  apiKey: string
  model: string
  // 各家差异点
  audioInputFormat?: 'openai-audio-part' | 'xiaomi-format' | 'none'
  streamingHeaderTransform?: (msg) => msg
}

class UnifiedOpenAICompatProvider implements LLMProvider {
  // 90% 通用代码
}

// providers 退化为配置:
export const DeepSeekProvider = makeProvider({ baseURL: '...', audioInputFormat: 'none' })
export const XiaomiProvider   = makeProvider({ baseURL: '...', audioInputFormat: 'xiaomi-format' })
export const OpenAIProvider   = makeProvider({ baseURL: '...', audioInputFormat: 'openai-audio-part' })
```

### 任务拆解
